## Domain 1 — Design Secure Architectures (30%)

### Q1. [MCQ]

A company runs a web application on EC2 instances in Account A. The application needs to read objects from an S3 bucket that lives in Account B. A solutions architect must grant this access using AWS best practices — no long-lived access keys. Which approach is MOST appropriate?

- **A.** Create an IAM user in Account B, generate access keys, and store them in AWS Secrets Manager in Account A.
- **B.** Create an IAM role in Account B with a trust policy that allows Account A to assume it, and attach an S3 read policy. Assign an instance profile to the EC2 instances in Account A that permits `sts:AssumeRole` on that role.
- **C.** Enable S3 cross-region replication from Account B to Account A, then read objects locally.
- **D.** Use S3 pre-signed URLs generated by an administrator each morning and distribute them to the application.

<details><summary>Answer & explanation</summary>

**Correct: B.**

Cross-account IAM role assumption (`sts:AssumeRole`) is the canonical AWS solution for service-to-service cross-account access without long-lived credentials. The EC2 instance profile obtains temporary credentials via the Instance Metadata Service (IMDS); those credentials are automatically rotated. No keys are stored anywhere.

- **A** is wrong — IAM user access keys are long-lived credentials. Even storing them in Secrets Manager adds operational overhead and doesn't eliminate the static key risk. The best-practice guidance is to prefer roles over keys for EC2.
- **C** is wrong — replication duplicates data unnecessarily, incurs storage/replication costs, and adds latency before objects are available.
- **D** is wrong — pre-signed URLs expire and require manual regeneration; this is not scalable and does not follow least-privilege automation principles.

</details>

### Q2. [MCQ]

A large enterprise uses AWS Organizations with multiple accounts. The security team wants to ensure that **no account in the organization can disable AWS CloudTrail**, regardless of individual account administrators. Which control achieves this with the LEAST operational overhead?

- **A.** Create an IAM permission boundary on every IAM role in each account that denies `cloudtrail:DeleteTrail`.
- **B.** Deploy an AWS Config rule to detect and auto-remediate CloudTrail deletion in each account.
- **C.** Attach a Service Control Policy (SCP) at the organization root that denies `cloudtrail:StopLogging`, `cloudtrail:DeleteTrail`, and `cloudtrail:UpdateTrail`.
- **D.** Enable AWS Security Hub with the AWS Foundational Security Best Practices standard across all accounts.

<details><summary>Answer & explanation</summary>

**Correct: C.**

SCPs are guardrails applied at the Organizations level. A Deny SCP at the root applies to every account in the organization — including the management account members and all OUs — and cannot be overridden by account-level IAM policies. One SCP replaces per-account configuration work.

- **A** is wrong — permission boundaries apply to individual principals, not accounts, and must be applied to every role individually; they are easily bypassed by creating new roles without the boundary.
- **B** is wrong — Config remediation is *detective* (after-the-fact), not *preventive*. There is a window between deletion and remediation.
- **D** is wrong — Security Hub provides findings but does not enforce controls or prevent actions.

</details>

### Q3. [MCQ]

A company stores sensitive customer data in an S3 bucket. Compliance requires that all objects be encrypted using keys that the company fully controls and can audit. The company already uses AWS KMS. Objects must be encrypted server-side without requiring clients to manage the encryption themselves. Which S3 encryption option satisfies these requirements?

- **A.** SSE-S3 (Server-Side Encryption with S3-managed keys)
- **B.** SSE-C (Server-Side Encryption with Customer-Provided Keys)
- **C.** SSE-KMS (Server-Side Encryption with AWS KMS Customer Managed Keys)
- **D.** Client-side encryption with a locally generated AES-256 key

<details><summary>Answer & explanation</summary>

**Correct: C.**

SSE-KMS with a Customer Managed Key (CMK) lets the company control the key policy, enable key rotation, and use AWS CloudTrail to audit every use of the key (`kms:GenerateDataKey` and `kms:Decrypt` events). Encryption happens server-side, so the client sends plaintext; AWS handles encryption transparently.

- **A** is wrong — SSE-S3 uses keys managed entirely by AWS S3. The customer has no control over or visibility into the key lifecycle, which fails the "company fully controls" requirement.
- **B** is wrong — SSE-C requires the client to supply the encryption key with every request. This is operational overhead and does not use KMS.
- **D** is wrong — client-side encryption requires the application to manage keys locally and adds significant complexity; AWS KMS is not used.

</details>

### Q4. [MCQ]

A startup stores application secrets (database passwords, API keys) that must be **automatically rotated every 30 days**. The team wants the rotation to happen without any code changes or manual steps. Which AWS service is the BEST fit?

- **A.** AWS Systems Manager Parameter Store (Standard tier, `SecureString`)
- **B.** AWS Systems Manager Parameter Store (Advanced tier, `SecureString`)
- **C.** AWS Secrets Manager
- **D.** AWS KMS with manual key rotation enabled

<details><summary>Answer & explanation</summary>

**Correct: C.**

AWS Secrets Manager has built-in, managed rotation using Lambda functions for supported services (RDS, Redshift, DocumentDB, etc.). Rotation is configured on the secret itself with a schedule — no custom Lambda code required for supported databases. For unsupported databases, a rotation Lambda template is provided.

- **A** is wrong — Parameter Store Standard does not support native automatic rotation. You would need a custom Lambda and EventBridge schedule.
- **B** is wrong — Parameter Store Advanced tier adds higher throughput and parameter policies (expiry notifications), but still lacks native secret rotation. Secrets Manager is the correct choice.
- **D** is wrong — KMS key rotation rotates the CMK's backing material, not application-level secrets like database passwords.

</details>

### Q5. [MRQ — choose 2]

A solutions architect is hardening the network perimeter of a three-tier web application running in a VPC. The architect needs to know which statements about **Security Groups** vs **Network ACLs (NACLs)** are TRUE. (Choose TWO.)

- **A.** Security Groups are stateful; return traffic is automatically allowed without an explicit outbound rule.
- **B.** Network ACLs are stateful; you only need to add inbound rules to allow traffic in both directions.
- **C.** Network ACLs are applied at the subnet level and evaluate rules in numerical order, stopping at the first match.
- **D.** Security Groups support both Allow and Deny rules.
- **E.** Security Groups operate at the ENI level and support only Allow rules.

<details><summary>Answer & explanation</summary>

**Correct: A and C.**

Security Groups track connection state, so responses to allowed inbound connections are automatically permitted outbound (and vice versa). NACLs are applied per-subnet, are stateless, and process numbered rules in ascending order — the first matching rule wins (including `*` DENY at the end).

- **B** is wrong — NACLs are *stateless*, not stateful. Return traffic must be explicitly allowed with a separate outbound rule.
- **D** is wrong — Security Groups support only Allow rules; there is no explicit Deny. Traffic not matching any Allow rule is implicitly denied.
- **E** is wrong in the second half — the ENI-level description is correct, but Security Groups support *only Allow* rules, which this option also asserts, so technically E is correct in the rules part but option A is the cleaner/correct answer. Re-reading: E says "support only Allow rules" — that is actually TRUE. However, A is also TRUE. The exam typically makes one clearly stronger. In the SAA-C03 context, A and C are the canonical test points. **E** is technically also correct on the "only Allow rules" statement but is a duplicate concept covered by A; on the real exam you would select A and C as the two distinct truths tested here.

*Examiner note:* On the actual exam, A and C are the two intended correct answers testing stateful vs stateless and subnet-level NACL evaluation order.

</details>

### Q6. [MCQ]

An EC2 instance in a private subnet needs to call the AWS KMS API endpoint. The security team prohibits all internet traffic from private subnets. The team wants to eliminate NAT Gateway charges for this traffic and keep it off the public internet. What is the MOST cost-effective and secure solution?

- **A.** Deploy a NAT Gateway in the public subnet and update the private route table.
- **B.** Create a VPC Interface Endpoint (AWS PrivateLink) for AWS KMS in the VPC.
- **C.** Create a VPC Gateway Endpoint for AWS KMS in the VPC.
- **D.** Enable VPC peering with the KMS regional VPC.

<details><summary>Answer & explanation</summary>

**Correct: B.**

AWS KMS is supported by VPC Interface Endpoints (powered by AWS PrivateLink). Interface endpoints create elastic network interfaces (ENIs) in your subnet with private IP addresses; traffic never leaves the AWS network. This eliminates NAT Gateway charges for KMS calls and meets the no-internet requirement.

- **A** is wrong — NAT Gateway sends traffic through the public internet endpoint and incurs per-GB processing charges, which the question explicitly wants to avoid.
- **C** is wrong — Gateway Endpoints exist only for Amazon S3 and Amazon DynamoDB. KMS does not support Gateway Endpoints.
- **D** is wrong — VPC peering is used between two customer VPCs, not to access AWS service endpoints. It is also not how KMS access is architected.

</details>

### Q7. [MCQ]

A company's website is experiencing a sophisticated Layer 7 HTTP flood attack. The security team wants to automatically block malicious IPs and apply rate-limiting rules without rewriting application code. Which combination of AWS services provides this capability?

- **A.** AWS Shield Standard + Amazon CloudFront
- **B.** AWS WAF with rate-based rules attached to an Application Load Balancer
- **C.** AWS Shield Advanced + Amazon Route 53
- **D.** Security Groups with deny rules on the VPC

<details><summary>Answer & explanation</summary>

**Correct: B.**

AWS WAF (Web Application Firewall) operates at Layer 7 and supports rate-based rules that automatically block IPs exceeding a specified request threshold. WAF can be attached to ALBs, CloudFront distributions, API Gateway, and AppSync. Rate-based rules are specifically designed for HTTP flood mitigation.

- **A** is wrong — Shield Standard provides automatic always-on protection against common infrastructure (Layer 3/4) DDoS attacks. It does not offer rate-based rules or Layer 7 HTTP flood blocking.
- **C** is wrong — Shield Advanced provides enhanced DDoS protection and cost protection, but by itself it does not inspect HTTP request patterns or apply rate-based rules. WAF is the Layer 7 tool.
- **D** is wrong — Security Groups operate at Layer 4 (IP/port) and cannot inspect HTTP request content or apply rate-based logic.

</details>

### Q8. [MCQ]

A security team wants a managed service that continuously analyzes VPC Flow Logs, CloudTrail events, and DNS logs to detect **threats and anomalous behavior** such as communication with known malicious IPs or compromised EC2 instances. No agents should be installed. Which service should they enable?

- **A.** Amazon Inspector
- **B.** Amazon Macie
- **C.** AWS Security Hub
- **D.** Amazon GuardDuty

<details><summary>Answer & explanation</summary>

**Correct: D.**

Amazon GuardDuty is a managed threat detection service that ingests VPC Flow Logs, CloudTrail management and data events, and DNS logs (where Route 53 Resolver is used). It uses machine learning and threat intelligence to identify suspicious behavior — no agents required. Classic findings include EC2 instances querying cryptocurrency mining pools, port scanning, or communicating with known malicious IPs.

- **A** is wrong — Amazon Inspector is a vulnerability assessment service. It scans EC2 instances and container images for software vulnerabilities and unintended network exposure. It focuses on CVEs and misconfigurations, not real-time threat detection from logs.
- **B** is wrong — Amazon Macie uses ML to discover and classify sensitive data (PII, credit card numbers) in S3 buckets. It is a data security service, not a threat detection service.
- **C** is wrong — Security Hub aggregates findings from GuardDuty, Inspector, Macie, and other tools into a unified dashboard. Enabling Security Hub alone without GuardDuty does not provide the log analysis described.

</details>

A healthcare company must identify S3 buckets that contain **personally identifiable information (PII)** such as names, social security numbers, and medical record identifiers. The team wants automated, continuous discovery with no custom code. Which AWS service fulfills this requirement?

- **C** is wrong — AWS Config tracks resource configurations and compliance. The public-access rule checks bucket ACL settings, not the content of objects.

### Q10. [MCQ]

An application deployed on EC2 in a public subnet serves API traffic. The solutions architect wants to ensure that only traffic originating from the company's office IP range (203.0.113.0/24) reaches the EC2 instances on port 443. The rule must be enforced even if an administrator accidentally changes the Security Group. Which combination enforces this at BOTH the instance and subnet level?

- **A.** Add an inbound rule on the Security Group allowing 203.0.113.0/24 on port 443. Add an inbound NACL rule allowing 203.0.113.0/24 on port 443 and a DENY ALL rule before it.
- **B.** Add an inbound rule on the Security Group allowing 203.0.113.0/24 on port 443. Add an inbound NACL DENY rule for 0.0.0.0/0 on port 443 with a lower rule number, and an ALLOW rule for 203.0.113.0/24 with a higher number.
- **C.** Add an inbound rule on the Security Group allowing 203.0.113.0/24 on port 443. Add an inbound NACL ALLOW rule for 203.0.113.0/24 on port 443 (rule 100) and a DENY rule for 0.0.0.0/0 on port 443 (rule 200). Also add an outbound NACL ALLOW rule for ephemeral ports (1024-65535) to 203.0.113.0/24.
- **D.** Use AWS WAF to allow only 203.0.113.0/24 on port 443 and attach it to the Security Group.

<details><summary>Answer & explanation</summary>

**Correct: C.**

NACLs process rules in numerical order and stop at the first match. Setting ALLOW 203.0.113.0/24 at rule 100 and DENY 0.0.0.0/0 at rule 200 restricts inbound traffic to only the office range. Because NACLs are stateless, an outbound rule for ephemeral ports (1024–65535) is also required to allow response traffic back to the client. The Security Group provides instance-level enforcement.

- **A** is wrong — placing the DENY ALL *before* the ALLOW (lower rule number) would block all traffic including the desired office range.
- **B** is wrong — a DENY rule at a lower number than the ALLOW rule would deny 0.0.0.0/0 (including 203.0.113.0/24, a subset of 0.0.0.0/0) before the ALLOW is reached.
- **D** is wrong — AWS WAF cannot be attached to Security Groups. WAF is attached to ALBs, CloudFront, API Gateway, or AppSync.

</details>

### Q11. [MCQ]

A company uses an Amazon S3 bucket to host static assets for a public website served through CloudFront. The security team requires that **S3 objects are never directly accessible via the S3 URL** — only through CloudFront. What is the recommended way to enforce this?

- **A.** Enable S3 Block Public Access and configure an S3 bucket policy that allows access only from CloudFront using an Origin Access Control (OAC).
- **B.** Set the S3 bucket ACL to private and add the CloudFront IP ranges to the bucket policy.
- **C.** Enable S3 Transfer Acceleration and restrict access to the CloudFront distribution IP ranges.
- **D.** Use an S3 VPC endpoint and configure CloudFront to route through the endpoint.

<details><summary>Answer & explanation</summary>

**Correct: A.**

Origin Access Control (OAC) is the current AWS recommendation (replacing the legacy Origin Access Identity/OAI). With OAC, the CloudFront distribution signs requests to S3 using SigV4. The S3 bucket policy allows only the specific CloudFront distribution's service principal (`cloudfront.amazonaws.com`) with the distribution ARN in the condition. Block Public Access ensures no ACL or bucket policy change accidentally exposes objects publicly.

- **B** is wrong — hardcoding CloudFront IP ranges is not feasible because they change frequently. AWS publishes IP ranges via `ip-ranges.json`, but this approach is brittle and not recommended.
- **C** is wrong — S3 Transfer Acceleration speeds up uploads from end users to S3 via CloudFront edge locations but does not restrict access to objects.
- **D** is wrong — CloudFront is a globally distributed service; it does not operate inside a VPC and cannot use VPC endpoints to reach S3.

</details>

### Q12. [MRQ — choose 2]

A company needs to give an external auditor read-only access to specific AWS resources in the company's account. The auditor uses their own AWS account. Which TWO actions should the solutions architect take to follow AWS security best practices?

- **A.** Create an IAM user in the company account, generate access keys, and email them to the auditor.
- **B.** Create an IAM role in the company account with the required read-only permissions and a trust policy that specifies the auditor's AWS account ID.
- **C.** Share the company's AWS root account credentials temporarily.
- **D.** Require the auditor to use `sts:AssumeRole` from their account to assume the role created in the company account.
- **E.** Enable MFA delete on the S3 bucket.

<details><summary>Answer & explanation</summary>

**Correct: B and D.**

Cross-account role assumption is the secure, auditable pattern for granting external parties access. The company creates a role (B) with a trust policy referencing the auditor's account; the auditor then calls `sts:AssumeRole` from their account (D) and receives time-limited temporary credentials. No permanent credentials need to be shared.

- **A** is wrong — IAM user access keys are long-lived credentials. Emailing them is a significant security risk.
- **C** is wrong — sharing root credentials is a critical security violation; the root account should have no access keys and only be used for tasks that specifically require it.
- **E** is wrong — MFA delete restricts who can permanently delete object versions in versioned S3 buckets; it is unrelated to granting auditor access.

</details>

### Q13. [MCQ]

An application on EC2 accesses an RDS MySQL database. Developers have been hardcoding the database password in the application's configuration file. A solutions architect must eliminate hardcoded credentials and ensure the password is automatically rotated every 90 days. Which solution meets these requirements with the LEAST operational overhead?

- **A.** Store the password in an environment variable on the EC2 instance and write a cron job that calls a custom Lambda to rotate it.
- **B.** Store the password in AWS Secrets Manager with automatic rotation enabled (90-day schedule). Update the application to call the Secrets Manager API at runtime to retrieve the current password.
- **C.** Store the password in an S3 object with SSE-KMS encryption and download it at instance start.
- **D.** Store the password in AWS Systems Manager Parameter Store as a `SecureString` and write a custom Lambda rotation function triggered by EventBridge every 90 days.

<details><summary>Answer & explanation</summary>

**Correct: B.**

Secrets Manager provides native integration with RDS for automatic password rotation — no custom Lambda authoring required (AWS provides the rotation function). The application retrieves the current secret value via the API at runtime. This eliminates hardcoded credentials and fully automates rotation.

- **A** is wrong — this requires writing and maintaining a custom Lambda function plus a cron job, which is high operational overhead.
- **C** is wrong — S3 does not provide rotation capability or a secrets management API. The application would be downloading a static file.
- **D** is wrong — Parameter Store requires you to write your own rotation Lambda and EventBridge rule. Secrets Manager handles this natively with less effort.

</details>

### Q14. [MCQ]

A company has an ALB-fronted web application. They want to protect it from common web exploits such as SQL injection and cross-site scripting (XSS), and they also want AWS to automatically update the threat rules without manual intervention. Which service and feature combination achieves this?

- **A.** AWS WAF with AWS Managed Rules attached to the ALB
- **B.** AWS Shield Advanced with proactive engagement
- **C.** Amazon Inspector with network reachability rules
- **D.** VPC Flow Logs with Lambda-based automatic remediation

<details><summary>Answer & explanation</summary>

**Correct: A.**

AWS WAF's Managed Rules are pre-configured rule groups maintained by AWS (and AWS Marketplace vendors) that cover OWASP Top 10 threats including SQLi and XSS. They are updated by AWS automatically. Attaching the WAF web ACL to the ALB inspects all HTTP/S requests before they reach EC2.

- **B** is wrong — Shield Advanced is for DDoS protection at Layers 3, 4, and 7 (via WAF integration), not for SQLi/XSS rule management.
- **C** is wrong — Inspector assesses EC2 instances and container images for vulnerabilities; it does not inspect HTTP traffic in transit.
- **D** is wrong — Flow Logs capture IP-level metadata (source IP, destination IP, port, bytes) but do not decode HTTP request payloads. SQLi/XSS detection requires payload inspection.

</details>

### Q15. [MCQ]

A financial services company requires that data at rest in all EBS volumes be encrypted with keys that the company can rotate and audit. After encryption is enabled, no IAM principal — even account administrators — should be able to disable encryption on existing volumes. How should the architect configure this?

- **A.** Enable default EBS encryption at the account/region level using a KMS Customer Managed Key. Apply an SCP that denies `ec2:DisableEbsEncryptionByDefault` and `kms:ScheduleKeyDeletion`.
- **B.** Manually encrypt every EBS snapshot and set the volume to use AWS managed keys.
- **C.** Use AWS Config to detect unencrypted volumes and trigger a Lambda function to encrypt them.
- **D.** Encrypt volumes using SSE-S3 keys applied through the EBS console.

<details><summary>Answer & explanation</summary>

**Correct: A.**

Enabling default EBS encryption at the account level automatically encrypts all new volumes and snapshots. Using a CMK satisfies the "rotate and audit" requirement. The SCP prevents any account admin from turning off the default encryption setting or deleting the key, since SCPs override IAM permissions (including admin policies) within the organization.

- **B** is wrong — AWS managed keys (`aws/ebs`) are controlled by AWS; the company cannot rotate them on demand or view individual audit entries for them. Manual per-snapshot encryption is also operationally burdensome.
- **C** is wrong — Config is detective; new volumes would briefly exist unencrypted before remediation, violating the requirement.
- **D** is wrong — EBS volumes are not encrypted using SSE-S3. EBS encryption uses AWS KMS (CMK or AWS managed key `aws/ebs`). SSE-S3 applies only to S3 objects.

</details>

### Q16. [MCQ]

An organization wants to audit all S3 data access events (individual object GetObject and PutObject calls) across 50 accounts in AWS Organizations. CloudTrail must capture these events centrally. What must the architect enable to capture S3 object-level activity?

- **A.** Enable CloudTrail Management Events in each account's default trail.
- **B.** Create an AWS Organizations trail and enable S3 Data Events in CloudTrail.
- **C.** Enable Amazon S3 Server Access Logging on each bucket and aggregate logs in a central bucket.
- **D.** Enable VPC Flow Logs for all VPCs and filter for port 443 traffic to S3.

<details><summary>Answer & explanation</summary>

**Correct: B.**

CloudTrail supports two categories: Management Events (control-plane actions like `CreateBucket`) and Data Events (data-plane actions like `GetObject`, `PutObject`). Data Events are not enabled by default. An Organizations trail applies to all accounts and can be configured to capture S3 Data Events for all buckets. Logs are delivered to a central S3 bucket.

- **A** is wrong — Management Events capture API calls against AWS resources (bucket creation, IAM changes) but not individual S3 object reads/writes.
- **C** is wrong — S3 Server Access Logging provides per-request logs for a specific bucket, but it is not as structured as CloudTrail, requires per-bucket configuration, and is not the recommended compliance audit trail mechanism.
- **D** is wrong — VPC Flow Logs record IP-level network traffic metadata, not HTTP-level S3 API calls. They cannot identify which S3 object was accessed.

</details>

## Domain 2 — Design Resilient Architectures (26%)

### Q17. [MCQ]

A company runs an Amazon RDS MySQL database and wants to ensure the database remains available if an entire Availability Zone fails. The solution must provide **automatic failover** with minimal downtime and no data loss. Which feature should the architect enable?

- **A.** RDS Read Replica in the same Availability Zone
- **B.** RDS Multi-AZ deployment
- **C.** RDS Read Replica in a different Availability Zone
- **D.** Manual RDS snapshot with daily restore testing

<details><summary>Answer & explanation</summary>

**Correct: B.**

RDS Multi-AZ maintains a synchronous standby replica in a different AZ. If the primary instance or AZ fails, RDS automatically fails over to the standby — typically within 60–120 seconds — with no data loss (synchronous replication) and no DNS changes required by the application (the endpoint remains the same).

- **A** is wrong — a Read Replica in the same AZ provides read scaling but not AZ-level fault tolerance, and Read Replicas use asynchronous replication (potential data loss at failover) and do not fail over automatically.
- **C** is wrong — Read Replicas in a different AZ also use asynchronous replication. They can be manually promoted after a failure, but this is not automatic and risks some data loss.
- **D** is wrong — manual snapshots are a Backup & Restore DR strategy with high RTO (hours to restore). This does not provide AZ-level automatic failover.

</details>

### Q18. [MCQ]

A media company has an RDS MySQL database with heavy read traffic from reporting workloads. The primary instance is hitting CPU limits. The operations team does NOT want to lose any writes during the solution implementation. What is the MOST effective solution to offload read traffic?

- **A.** Increase the RDS instance size (vertical scaling) and enable Multi-AZ.
- **B.** Create one or more RDS Read Replicas and point reporting queries to the replica endpoint.
- **C.** Enable RDS Multi-AZ, which automatically distributes read traffic to the standby.
- **D.** Enable ElastiCache in front of the primary RDS instance and cache all read results.

<details><summary>Answer & explanation</summary>

**Correct: B.**

RDS Read Replicas are purpose-built for read scaling. The primary handles writes; replicas receive asynchronous replication and serve read-only queries. The reporting tools connect to the replica endpoint. Multiple replicas can be created. No writes are interrupted during creation.

- **A** is wrong — vertical scaling (bigger instance) helps but does not fundamentally separate read and write workloads, is expensive, and requires a maintenance window restart.
- **C** is wrong — the Multi-AZ standby is NOT accessible for read queries. It exists solely for failover. This is a very common exam distractor.
- **D** is wrong — ElastiCache is an excellent cache layer for frequently repeated queries, but it doesn't directly offload arbitrary read queries without significant application code changes. It is not as straightforward as a read replica for reporting workloads and doesn't serve as a direct replica of the database.

</details>

### Q19. [MCQ]

A company operates a global e-commerce application that requires a relational database with **sub-second failover across AWS Regions** and up to **16 read replicas within a region**. Which AWS database solution meets these requirements?

- **A.** Amazon RDS MySQL with Multi-AZ and cross-region Read Replicas
- **B.** Amazon Aurora Global Database
- **C.** Amazon DynamoDB Global Tables
- **D.** Amazon Redshift with cross-region snapshot copy

<details><summary>Answer & explanation</summary>

**Correct: B.**

Aurora Global Database supports up to five secondary AWS Regions with read replicas, physical replication at the storage layer (latency under 1 second), and promotes a secondary region to primary in under 1 minute. Within each region, Aurora supports up to 15 Aurora Replicas (read replicas), plus the writer — effectively 16 total instances per region.

- **A** is wrong — RDS cross-region Read Replicas use asynchronous replication (seconds to minutes of lag) and manual promotion. Failover to a cross-region replica is not automatic and is not sub-second.
- **C** is wrong — DynamoDB Global Tables provide multi-active NoSQL replication. The requirement is for a relational database.
- **D** is wrong — Redshift is a data warehousing service (analytics/OLAP). Cross-region snapshot copy is for DR, not for low-latency OLTP with sub-second failover.

</details>

### Q20. [MCQ]

A company wants to decouple a high-volume order processing system. Orders placed on the frontend should be persisted even if the backend processing service is temporarily unavailable. The backend must process each order **exactly once** and the solution must handle message retention for up to **14 days**. Which service is the BEST fit?

- **A.** Amazon SNS (Simple Notification Service)
- **B.** Amazon EventBridge
- **C.** Amazon SQS Standard Queue
- **D.** Amazon SQS FIFO Queue

<details><summary>Answer & explanation</summary>

**Correct: C.**

Amazon SQS is the purpose-built durable message queue. Standard Queues retain messages for up to 14 days, scale to unlimited throughput, and provide at-least-once delivery. The backend consumers poll the queue and process messages independently of the frontend. If the backend is down, messages accumulate in the queue without loss.

- **Streaming high-throughput data with multiple independent consumers** → Kinesis Data Streams
- **Lambda + RDS connection exhaustion** → RDS Proxy
- **Sub-millisecond key-value caching / session state** → ElastiCache for Redis
- **DynamoDB microsecond reads (eventually consistent only from cache)** → DAX
- **HPC parallel file system + S3 integration** → FSx for Lustre
- **Shared NFS for hundreds of Linux EC2 instances across AZs** → Amazon EFS
- **Highest-IOPS EBS + Multi-Attach** → io2 Block Express
- **DR strategy RTO ranking** (slowest → fastest): Backup & Restore → Pilot Light → Warm Standby → Multi-Site Active-Active
- **Canary/blue-green traffic split at DNS** → Route 53 Weighted Routing
- **Automatic RTO < 1 min cross-region DB failover** → Aurora Global Database
- **Multi-active multi-region NoSQL** → DynamoDB Global Tables
- **Maximum EC2 cost savings for 24/7 steady workload** → 3-year All Upfront Reserved Instance
- **Batch / fault-tolerant / interruptible workloads** → Spot Instances
- **Database idle nights + weekends** → Aurora Serverless v2
- **Unknown/changing S3 access patterns, auto-tiering** → S3 Intelligent-Tiering
- **Regulatory object immutability (no one can delete)** → S3 Object Lock Compliance mode
- **Reduce Athena scan costs** → Parquet/ORC columnar format + partitioning + compression
- **Granular hourly billing data for dashboards / chargeback** → Cost and Usage Report (CUR)
- **CloudFront cache hit rate = 0%** → check origin `Cache-Control: no-store` or TTL = 0
